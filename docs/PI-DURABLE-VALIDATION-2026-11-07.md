# PI-Durable 验证方案

日期：2026-11-07。

依据：`PRODUCT-PI-PLAN-2026-11-06.md` 第 4 节（Core / Durable 的前置验证）与第 4.1～4.2 节的版本顺序和适配要求；当前 `feature/desktop-pi` 工作区的 Core 1.4.0 实现与 stdio 协议（`pi-worker/src/protocol.js`、`PiWorkerProcess.java`）。

状态：待执行的验证方案。本文不产生"已采用 Durable"的结论；验证分支或原型不算新增正式生产引擎。所有结论以实际锁定版本的实测证据为准。

## 1. 目的与边界

在自建会话压缩、恢复和任务队列之前，验证 pi-durable 能否以更低的自有代码量承接这些机制。验证只回答规划文档第 4 节的六个问题：

| 编号 | 验证问题 | 本文对应章节 |
| --- | --- | --- |
| Q1 | 能否复用 Java 工具 | 第 4 节 |
| Q2 | 能否复用产品事件 | 第 5 节 |
| Q3 | 是否满足会话策略 | 第 6 节 |
| Q4 | 恢复是否符合产品语义 | 第 7 节 |
| Q5 | 是否适合桌面分发 | 第 8 节 |
| Q6 | 是否减少维护负担 | 第 9 节 |

不在本次验证范围内：

- 写入工具与审批的完整迁移（属阶段 E）；但"审批等待期间的恢复"作为恢复语义的验证场景保留，使用模拟工具，不接触真实写入。
- Explorer 并行化、Planner、团队权限、业务知识系统。Durable 不自动提供这些，验证也不承诺。
- Coding Agent SDK、上游终端界面与更新器。
- 生产环境性能指标。所有耗时为单次场景记录，不代表 p95。

## 2. 前置条件

按规划文档第 4.1 节的顺序执行，前一项不通过不进入下一项：

1. **Core 1.4.0 基线冻结**。以现有 MySQL / DM8 固定任务集的实测结果（正确率、耗时、Token、工具调用次数、终态形态）作为对比基线，记录模型版本、数据集、预算与测量环境。PI-M2 报告格式可复用。
2. **Core / pi-ai 1.5.0 单独升级验证**。固定依赖与 lockfile，复测现有 Worker 与 Java 工具链，重点覆盖第 4.2 节的 pi-schema 校验迁移与流式参数增量解析：缺失字段、非法类型、额外字段、边界数值、枚举、长参数分块、取消与终态。记录全部行为差异。
3. **Durable 原型构建**。使用与 Core 1.5.0 匹配的 pi-durable 1.5.0 及 `chord`，单独分支。优先使用随版本提供的 SQLite / JSONL 存储实现，不自定义存储后端。采用前按锁定版本核对 README 与 CHANGELOG 中的实际 API，不照搬旧 `watchEvents()` 与旧 `Storage.commit()` 签名。

验证全程 Durable 与 Core 使用相同模型版本、工具范围、数据集、权限与预算；框架收益不得混入 1.4 → 1.5 的版本变化。

## 3. 原型架构与协议改造点

原型沿用"Java 宿主 + Node Worker"边界：Durable 只替换 Worker 内的 Agent 运行时，Java 继续负责连接管理、工具校验、预算、执行与凭证。现行 stdio 协议（版本 1）需要以下改造，逐项在原型中验证：

| 编号 | 改造点 | 现行行为 | Durable 下需要验证的行为 |
| --- | --- | --- | --- |
| P1 | 进程与生命周期 | 进程死 = 会话死；30 分钟空闲退出；stdin 关闭即退 | 进程死 = 任务挂起待恢复；有空闲退出前 drain 或明确挂起的语义；Java `close()` 不再等于终止任务 |
| P2 | `hello` 握手 | 仅协议版本与包版本检查 | 增加恢复清单：重开存储后存在的会话、运行中任务、等待工具结果与等待审批的任务；Java 内存运行表能从清单重建 |
| P3 | `start` 幂等 | 重发即重复运行 | 带稳定幂等键的提交；Worker 重启后重发同一请求 attach 到既有运行，不产生第二次模型调用 |
| P4 | 事件流 | Worker 内存订阅实时转发 `text_delta`，断线即丢 | Java 重连后可按 Entry 偏移续传，补齐断线期间的文本与工具事件；推送带序号并去重；按 v1.5.0 的会话状态视图订阅实现，不复用旧 `watchEvents()` |
| P5 | 工具调用幂等 | `tool_call` 实时发出，`tool_result` 即发即弃 | Worker 重启后同一 `toolCallId` 可能重发：Java 去重并返回缓存结果，不重复执行；结果可迟到交付 |
| P6 | 终态跨进程 | start 与 finished 同一进程 | finished 可能由另一进程实例发出；Java 的 terminal 标志、计费与清理逻辑可接受跨进程终态；每 run 仍恰好一条 finished |
| P7 | `cancel` 语义 | 发消息 + 杀进程兜底 | 取消经 Harness 持久记录；区分"取消等待"与"取消工作"；Java 收到持久化确认才算取消成功；杀进程不再作为取消手段 |
| P8 | 协议版本 | 版本 1 | 升级到版本 2，`hello` 协商 durable 能力；过渡期内新旧协议并存，Java Agent / Core / Durable 可三路对照 |

状态来源原则：迁移后任务与 transcript 的唯一事实来源是 Durable 存储，Java 内存状态降级为视图。任何 Java 与 Worker 同时推进同一任务的设计都视为验证失败。

## 4. Q1：Java 工具复用验证

复用现有四个只读工具（`list_tables` / `describe_table` / `describe_tables` / `query_database`）与主助手发现工具（`list_connections` / `list_namespaces`），工具执行仍在 Java。

| 场景 | 通过标准 |
| --- | --- |
| 固定任务集全量 | DM8 与 MySQL 各跑一遍，结果与 Core 基线一致；目标范围、连接版本校验、15 秒超时、200 行上限、截断标记全部保留 |
| 非法工具参数 | pi-schema 校验失败信息经 Worker 回到模型；Java 侧最终校验仍然拦截，不依赖 Worker 校验 |
| 预算 | `maxModelCalls` / `maxToolCalls` 语义在 Durable 任务模型下等价；超限产生与基线一致的失败终态 |
| 凭证边界 | API Key 仍只经 stdin 传入；存储文件、transcript、任务 JSON 与诊断输出中不出现密钥（用固定样例密钥全文检索验证） |

## 5. Q2：产品事件复用验证

前端不做框架感知改造，由 Java 将 Durable 事件映射为现有事件契约。

| 场景 | 通过标准 |
| --- | --- |
| 文本流式 | text 增量在现有界面逐块渲染；注意 v1.5.0 `progress.persistWithinMs` 默认 1000 ms：区分"已展示进度"与"已持久化状态"，不向用户承诺每个可见增量已保存 |
| 工具调用展示 | 工具名、参数、执行编号、状态、截断标记与基线一致 |
| 子任务 | Explorer 委派在界面上的展示与基线一致；Durable child task 与现有 Explorer 进程的对应关系明确记录 |
| 失败与取消 | 模型失败、工具失败、取消各自产生基线一致的界面终态 |
| 唯一终态 | 每 run 恰好一个 DONE；含取消场景（收到 TEXT 后取消只产生一个 CANCELLED DONE） |

## 6. Q3：会话策略与存储内容清单

验证"实际保存了什么"，而不是引用 Durable 文档的说法。

| 工作 | 证据要求 |
| --- | --- |
| 存储内容清点 | 跑完固定任务集后导出 SQLite / JSONL 全文，逐类列出：用户消息、模型输出、系统提示词、工具参数、工具结果、任务状态、用量记录、trace carrier。标注每类的保留周期与清理方式 |
| 凭证扫描 | 在存储文件与转储中检索样例 API Key 与数据库密码，命中即为失败 |
| 关闭与清理 | 删除会话后存储中对应 transcript、任务与文档条目实际移除；应用卸载/清理目录后无残留 |
| 内存模式对照 | 以 `MemoryStorage` 跑同一任务集，确认仅丢失恢复能力、其余行为一致；量化两种模式各自买到的能力，为"是否落盘"的产品决策提供依据 |
| 产品决策更新 | 当前策略为"完整聊天历史不持久化"。若采用落盘存储，须先更新产品说明与数据策略；不能同时承诺完全不保存上下文与完整任务恢复 |

## 7. Q4：恢复语义验证

核心场景，逐项实测并录像或留存日志证据：

| 场景 | 操作 | 通过标准 |
| --- | --- | --- |
| R1 模型请求中途崩溃 | 模型流式输出中途杀 Worker | 重启后该请求按失败尝试重试；重试预算有限；不会产生无限重启；界面终态唯一 |
| R2 工具执行中途崩溃 | Java 收到 `tool_call` 后、返回 `tool_result` 前杀 Worker | 重启后同一 `toolCallId` 重发，Java 去重返回缓存结果；查询不重复执行（用执行日志计数证明） |
| R3 Java 崩溃 | 运行中途杀 Java 宿主 | Java 重启后能从 `hello` 恢复清单重建运行表，attach 续传事件；不虚报失败也不静默丢失 |
| R4 双方同时崩溃 | 先后杀 Worker 与 Java | 依次重启后运行可恢复或产生明确终态；无悬挂"运行中" |
| R5 审批等待恢复 | 用模拟审批工具挂起 run，杀双方进程再重启 | 恢复后审批入口仍在；用户拒绝与批准分别产生对应终态；未经确认的写入类动作不重放 |
| R6 取消的持久性 | 取消后立即杀 Worker | 重启后该任务保持已取消，不复活 |
| R7 崩溃窗口 | 在 `progress.persistWithinMs` 窗口内杀进程 | 丢失的增量不超过窗口；恢复后界面明确区分已持久化与已丢失部分，不补造内容 |
| R8 重复提交 | Worker 重启后 Java 重发同一 `start` | attach 到既有运行，无第二次模型调用，无重复计费 |

恢复语义的产品边界：明确列出哪些任务恢复、哪些中断及理由。写入结果为 UNKNOWN 时先核对数据库事实，不自动重试（与规划文档第 5 节一致）。

## 8. Q5：桌面分发验证

| 场景 | 通过标准 |
| --- | --- |
| 依赖锁定 | pi-durable、chord、pi-ai 与 SQLite 依赖全部锁定版本与 lockfile；记录安装体积增量 |
| Node 运行时 | SQLite 存储若使用原生模块，验证目标平台（macOS / Windows）的预编译产物或编译链可用；不在用户机器上要求编译环境 |
| 启动退出 | 干净目标机器上安装、启动、跑一条只读任务、退出；存储文件位置符合应用数据目录约定 |
| 存储健壮性 | 存储文件被占用、只读、损坏时的启动行为明确，不静默丢会话 |
| 升级 | 锁定版本升级时存储格式迁移路径有官方依据；无官方迁移承诺则记录为风险项 |

## 9. Q6：维护负担对比

逐项列出三份清单并附代码量与测试数：

1. **可删除**：采用 Durable 后可以移除的自建代码（或未来不必再写的：压缩、恢复、任务队列）。
2. **需保留**：Java 工具校验、预算、审批、协议适配层、事件映射；明确这些不因 Durable 消失。
3. **需新增**：协议版本 2、幂等与去重、恢复清单处理、存储管理、Durable 版本升级适配（实验性 API 的跟踪成本单列）。

记录接口变动成本：本次验证中因 Durable API 与文档预期不符而调整的次数与位置，作为"实验性"定性的实测依据。

## 10. 决策出口

验证完成后按以下规则记录结论，三者取一：

1. **采用 Durable**：Q1～Q5 全部通过，且 Q6 显示净减负。明确迁移范围、回退方案（作用于后续新会话，不在失败运行中换引擎重放）与遗留自建项。
2. **继续 Core**：任何一项 Q1～Q5 不通过或 Q6 显示净增负。记录具体原因与复评触发条件（如 Durable 脱离实验状态、特定版本修复、产品明确提出后台任务需求）。
3. **有限采用**：仅 MemoryStorage 模式承接任务机制与压缩，不落盘。需单独论证为何值得为此引入实验性依赖。

不允许将"完成调研"写成"已采用 Durable"；结论记录到规划文档 NEXT-02 的交付物中，附本方案各场景的实际证据链接。

## 11. 风险与开放问题

| 项 | 说明 |
| --- | --- |
| 实验性 API | v1.5.0 官方标记实验性，API 可能随时变更；升级需重新验证，不静默追随最新版 |
| 存储格式承诺 | 上游对 SQLite / JSONL 格式的跨版本兼容性承诺需按锁定版本核实 |
| 双状态源 | 过渡期 Java 与 Worker 各自持有任务状态，恢复清单（P2）未验证前不得扩大原型范围 |
| 写入幂等 | Durable 的任务日志不保证业务写入只执行一次；审批绑定不可变请求的设计属阶段 E，本次仅验证恢复语义 |
| 首字延迟 | Durable 的"先落盘后展示"与落盘窗口可能增加首字延迟；与 Core 基线同条件记录，不预设可接受 |
